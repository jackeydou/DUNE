# edge, CLI, and console

`edge` is the only public entry point. It authenticates callers, owns users, tenants, and
workspaces, serves the console, and forwards to the internal services. The `swarm` CLI and the
web console are its two clients. Their place among the services is in
[architecture.md](../architecture.md).

**Status:** not built. All three arrive in M4, once M0–M3 are done. Until then, runs are
triggered through the orchestrator's Control API on the internal network. Items marked
*(proposed)* go beyond what the specs decided; they are listed under [Not settled](#not-settled).

## edge

Go.

- **Public API.** Connect (connect-go) handlers generated by buf from `proto/`. One definition
  serves HTTP/JSON to the browser and gRPC to the CLI. Server streaming carries live run events.
- **Forwarding.** Run and case calls go to the orchestrator's `ControlService`. Analysis calls go
  to `AnalysisService`. The two sit side by side in the public API, and neither is nested under
  the other. Internal calls use gRPC with mTLS, and edge is the only caller that the Control API
  and analysis accept from M4 on.
- **Live events.** edge relays `ControlService.StreamEvents` to the browser.
- **Authentication.** Every call needs credentials. There is no anonymous access, the CLI
  included. The mechanism is not decided. The likely shape is OIDC sessions for the browser and
  personal API tokens for the CLI *(proposed)*.
- **Authorization.** Every authenticated caller sees every workspace. `workspace` is already a
  required field on cases, runs, and events, so per-workspace isolation later means adding a filter
  and a check in edge, with no data migration.
- **Storage.** The `tenant` schema in the shared Postgres, holding users, tenants, workspaces, and
  tokens. No other service reads it.
- **Console assets.** The built console is embedded in the binary with `embed.FS` and served by
  edge *(proposed)*.

## swarm CLI

Go, with cobra. It ships as one static binary, so users need no Python.

It is a client of edge and nothing more. There is no in-process path to the runtime:
`swarm run cases/x` packs the case directory and asks edge to submit it. The CLI imports no
`swarmeval` code and never imports `inspect_ai`. Its commands (`run`, `view`, `query`, `replay`,
`env up`, `export`) are listed in spec §8. For local development it may start a local instance
when none is reachable, but it calls that instance through the same API.

The endpoint and token come from a config file or the environment *(proposed)*.

## Console

React + Vite in the top-level `console/` project, with its own README and changelog. It imports
no `swarmeval` code. It calls edge through a client generated by buf *(proposed: Connect-ES)*.

The replay viewer shows one lane per agent plus lanes for the network and the environment. Clicking
an event expands its causal chain through `parent_id`, events can be filtered by tag, and two runs
can be compared side by side.

## Tech choices

| Need | Choice | Why |
|---|---|---|
| Public API | `connectrpc.com/connect` | One proto definition serves JSON to browsers and gRPC to the CLI, with no hand-written gateway |
| Postgres (`tenant`) | `github.com/jackc/pgx/v5` | The standard maintained Go driver *(proposed)* |
| CLI | `github.com/spf13/cobra` | The de facto standard, used by kubectl and gh |
| Console | React + Vite | See [tech-stack.md](../tech-stack.md) |
| Browser client | `@connectrpc/connect-web` | Generated from the same protos as the Go side *(proposed)* |

## Not settled

1. Where the Go module lives, and whether it gets its own changelog
   ([repo-layout.md](../repo-layout.md#where-new-code-goes)).
2. The authentication mechanism.
3. Migrations for the `tenant` schema. The rest of the database uses Alembic from Python, and edge
   is Go.
4. Embedding the console in edge versus serving it separately.
5. Per-workspace authorization (spec §9, question 8).
